## Patch and compatibility

The patch upgrades the Agent's npm Undici transport from 8.10.2 to 8.12.2 and
pins affected transitive major versions to 6.29.1 and 7.30.1. A synthetic local
response reproduced the old subprocess crash after fetch rejection was caught.
The fixed malformed request still fails; the intended guarantee is that it does
not terminate the subprocess and a subsequent healthy request can complete.

Electron is updated from 43.6.0 to 43.8.3 within the same major. Its
[compromised eMudhra intermediate-certificate mitigation](https://github.com/electron/electron/security/advisories/GHSA-jr5w-w6x2-84p9)
protects Chromium and Node TLS; the official minimum fixed 43.x version is 43.8.1
and the maintainer reports no application-level workaround. This reachable TLS
issue requires the runtime upgrade independently of the npm transport repair.

Account and update clients explicitly use Chromium networking with browser
session cookies omitted, preserving their explicit authorization headers,
cancellation, redirect restrictions and configured proxy behavior. Runtime
default, environment-proxy and custom-proxy routes use the patched npm fetch
implementation and its matching Request/Response types. Certificate validation,
origin checks, account isolation and permission controls are retained.

Website account login, automatic synchronization of allowed conversational
models, website recharge and credit refresh, existing API providers, conversations
and permission settings remain. No data-directory move or schema migration is
introduced by this patch. It requires no new Gateway deployment or billing change.
Installation remains manual; the client does not install updates automatically.

## Local qualification history

Before reboot, on the release owner's macOS 26.5 machine, the disposable packaged
credential probe remained blocked even after the screen was unlocked and the user
manually unlocked the Keychain from a terminal. A generated test item returned
`SecItemAdd` status `-25293` (authentication failure); independent helpers and
Apple's system tool reproduced the failure. A locked screen alone did not explain
these results, and the evidence did not establish a test-copy signing identity
as their cause. Publication was held while this independent gate failed.

The app failed closed when protected credential storage was unavailable. No
plaintext fallback, Keychain reset, deletion of user credentials or broad security
exception was introduced. Existing BYOK and conversation data were not modified
by these isolated tests. The later passing evidence below does not replace or
reclassify these earlier failures.

## Local macOS follow-up after screen and CLI unlock

The user confirmed screen unlock and a manual `security unlock-keychain` attempt.
A fresh packaged-copy probe still could not encrypt. Independently, a native
Security.framework helper and Apple's own `security` utility could not create
a unique generated test item (`errSecAuthFailed`, -25293), even though metadata
reported the default login Keychain unlocked/readable/writable.

The user then launched a separate, uniquely named, offline diagnostic through
Finder. At `2026-10-25T09:29:22.383Z`, first encryption remained blocked; its
security session matched the automation session (100002). It did not read the
installed application's profile or any real credential. This evidence does not
prove that all existing Keychain reads fail, that the user entered an incorrect
password, or that deleting/resetting the Keychain is necessary. The application
continues to reject account sign-in when protected storage is unavailable.

The first version of that diagnostic crashed before JavaScript because its
renamed bundle name did not match its Helper filename. This diagnostic-only
packaging mistake was fixed and its normal result-dialog startup and exit were
actually verified before the user's subsequent test. It is not an application
release regression or evidence of successful/failed Keychain access by itself.

At that stage, all native CI gates were passing but local qualification and
publication remained held. No real account login, plaintext fallback, Keychain
reset, installed-app replacement, or user-data migration was performed.

## Complete dependency assessment

The initial five-record GitHub view was not a full dependency audit. After the
Undici repair but before the Electron upgrade, the full-lockfile audit reported
75 package/advisory records and 54 distinct GHSAs. The updated lockfile reports
**68 records and 47 distinct GHSAs**, with no Electron or Undici registry record.
The full audit remains **not clean**. The
[machine-readable audit snapshot](1.1.1-dependencies.json) retains every record,
its dependency paths, source and lockfile hashes, and the scope limitations.

| Registry severity | Package/advisory records | Distinct advisories |
| --- | ---: | ---: |
| Critical | 3 | 3 |
| High | 38 | 26 |
| Moderate | 19 | 11 |
| Low | 8 | 7 |
| Total | 68 | 47 |

These counts include development/build tooling and conditional Renderer/SDK
findings. A dependency's `dev` label alone does not prove it is absent from the
application. The following assessed conditions do not erase package advisories:

- Tinypool's two critical records require prior prototype pollution in a Vitest
  worker environment. That development dependency is not the packaged account
  authentication endpoint.
- DOMPurify's template/DOM-output and in-place/detaching-hook findings retain
  the registry critical/high labels even though maintainer advisories label them
  Low. Current Mermaid code sanitizes strings to strings without the specified
  template/DOM-return/shadow-root or detaching-hook combinations. No applicable
  exploit was confirmed; this is not a general Renderer XSS exemption.
- KaTeX's restriction bypass requires pre-existing prototype pollution. Markdown
  sanitization occurs before KaTeX and is not claimed as a post-render defense.
  No current source of that pollution was established; conditional risk remains.
- Optional SDK Zod parsing, native-updater YAML and project resource globs have
  different prerequisites from the account/provider path and manual JSON update
  flow. These packages are not declared fixed by this patch.
- Other build, documentation and test findings remain maintenance debt. Executing
  untrusted repository code remains unsafe regardless of these feature tests.

Electron 43.8.3 still embeds Undici 7.29.1, and the Pi SDK contains older vendored
CLI parser bytes. The patch routes the affected production account/update/Agent
requests through Chromium or the patched npm transport. It does **not** claim
that every old parser copy was removed or that the Electron binary's built-in
Undici was upgraded. CSP and sandboxing do not make genuine Renderer XSS harmless.
